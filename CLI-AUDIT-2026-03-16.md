# Voyagier CLI — Agentic Readiness Audit

> **Date:** March 16, 2026
> **Auditor:** Wally (OpenClaw consigliere)
> **Codebase:** `Voyagier-Travel/voyagier-cli` @ main (post-PR #30)
> **Version:** 1.0.0 (12,075 LOC, 27 source files, 156 tests)
> **Context:** Preparing the CLI for use by human travel advisors and AI agents (Wally, Claude Code, Gemini, third-party agents)

---

## Executive Summary

The Voyagier CLI has excellent bones. All 29 GraphQL operations from the design doc are implemented. The 3-layer architecture (CLI → Skills → MCP) is the right call. `--json` on every command gives agents a clean interface. The booking pipeline works end-to-end.

But it's not agent-ready yet. Three things block autonomous use: agents can't recover from errors (47 `process.exit` calls), the skill docs are fragmented and stale, and JSON output fields are inconsistent. These are fixable in a day.

There's also overengineering to prune — 5 separate SKILL.md files that should be 1, a `--agent` flag that duplicates what `--json` already does, and a composite `plan-trip` command that agents don't actually need.

**Readiness score: 70%.** Fix the Tier 1 issues and it's 90%+.

## The Three Users

Every finding is evaluated against three personas:

1. **Wally (AI consigliere)** — Chains CLI commands via shell, parses `--json`, hands plan URLs to humans. Needs: reliable exit codes, consistent JSON, one skill file to read.
2. **Travel advisor (human)** — Uses CLI daily to build and manage trip plans. Needs: clear help text, workflow-ordered commands, good error messages.
3. **Third-party AI agents** — Reads SKILL.md, calls commands, parses output. Needs: complete documentation, recoverable errors, predictable output.

## Overengineering Assessment

Before the findings: what should we *stop* investing in?

### Overengineered (simplify or freeze)

| Item | Why It's Too Much | Recommendation |
|------|-------------------|----------------|
| **5 separate SKILL.md files** | Agents read one file, not five. Cross-references add confusion. Wally's single-file skill is better. | Consolidate to 1 comprehensive SKILL.md |
| **`--agent` flag on 11 commands** | `--agent` outputs markdown for displaying to humans *via* agents. But agents can format markdown from `--json` trivially. `--json` is the real agent interface. | Freeze `--agent` investment. Don't add to remaining commands. Keep what exists. |
| **`plan-trip` composite command (503 LOC)** | Agents chain simple commands better than calling one mega-command. `plans create` + `search flights` + `select` is more debuggable and composable. | Keep as convenience, don't expand. Not the agent path. |
| **Airport data file (6,012 LOC)** | 5,958 airports when Sabre covers maybe 3,000 commercial routes. Works fine, but was the least impactful feature. | Shipped, leave it. Don't invest more. |
| **Metro area groupings** | Solves a problem agents don't have (agents know IATA codes). Useful for humans occasionally. | Shipped, leave it. |

### Correctly Engineered (keep investing)

| Item | Why It's Right |
|------|----------------|
| 3-layer design (CLI → Skills → MCP) | Universal agent compatibility without MCP dependency |
| `--json` on every command | The actual agent interface. Consistent, parseable, complete. |
| Local state files (last-search.json) | Elegant numbered selection flow, necessary for the search→select chain |
| Plan URL in every output | Critical for CLI↔web switching, the product's key differentiator |
| `chat --message` | Enables non-interactive AI queries — important for agent use |
| 2 runtime deps (chalk + commander) | Minimal footprint, fast install |

## Findings

### 🔴 Tier 1: Fix These or Agents Break

#### 1.1 — `process.exit(1)` Kills Agent Workflows

**Severity:** 🔴 Critical
**Instances:** 47 across all command files
**Impact:** When an agent calls `voyagier plans list` and gets a 400 error, the process dies. The agent can't catch the error, inspect it, retry with corrected input, or report a structured failure. Every validation failure, auth error, and API hiccup is a hard crash.

**Example:**
```typescript
// Current: agent loses control
if (!opts.plan) {
  fatal("--plan is required");  // → process.exit(1)
}

// Should be: agent can catch and handle
if (!opts.plan) {
  throw new CliError("MISSING_FLAG", "--plan is required");
}
```

**Fix:** Create a `CliError` class with error codes. Replace all `process.exit(1)` calls with thrown errors. Add a top-level catch in `index.ts` that formats the error (JSON for `--json` mode, human-readable otherwise) and exits with appropriate code.

**Effort:** 3 hours
**Files:** All `src/commands/*.ts`, `src/output.ts`, `src/index.ts`

---

#### 1.2 — Skills Are Fragmented and Stale

**Severity:** 🔴 Critical
**Impact:** An agent reading the shipped skills gets an incomplete and outdated picture of the CLI.

**Problems with shipped skills (5 files in `skills/`):**

| Issue | Details |
|-------|---------|
| Fragmented | 5 files requiring cross-references. Agent must read all 5 to understand the tool. |
| Missing commands | `plans update`, `plans comments`, `plans vote`, `plans items`, `plans remove-item`, `plans invites`, `bookings get`, `travellers update` — all undocumented |
| Missing flags | `--agent`, `--active`, `--plan` on plan-trip, `chat --message`, `--stacktrace` — all undocumented |
| Missing features | Airport city name resolution, metro areas, piped stdin for chat — undocumented |
| Stale examples | Skills don't mention `--agent` output mode at all |
| No troubleshooting | Wally's local skill has "Known Quirks" section; shipped skills don't |

**Comparison:** Wally's single-file skill (`~/clawd/skills/voyagier-cli/SKILL.md`) is more complete, more practical, and easier for an agent to consume than the 5 shipped files combined.

**Fix:** Replace the 5-file structure with one comprehensive `skills/SKILL.md` that covers: auth, all commands, all flags, workflow examples, output modes, known quirks, and security rules.

**Effort:** 2 hours
**Files:** `skills/` directory (restructure)

---

#### 1.3 — Inconsistent `--json` Output Fields

**Severity:** 🔴 Critical
**Impact:** An agent parsing JSON output gets different field names for the same concept depending on which command it calls.

**Inconsistencies found:**

| Field | Commands using `url` | Commands using `tripPlanUrl` | Commands with neither |
|-------|---------------------|-----------------------------|-----------------------|
| Plan URL | `search.ts` | `plans.ts`, `plan-trip.ts` | `travellers list`, `bookings list` |

**Other issues:**
- `plans create --json` output structure differs from `plans get --json`
- `plan-footer.ts` returns `planSummary` object in some JSON outputs but not others
- `select --json` has different structure for flight vs hotel selections

**Fix:** Audit every `--json` output path. Standardize on:
- `url` for the plan URL (shorter, matches REST conventions)
- Always include `url` when a plan context exists
- Document the JSON schema for each command in the SKILL.md

**Effort:** 1 hour
**Files:** All `src/commands/*.ts`

### 🟡 Tier 2: Improve Quality of Life

#### 2.1 — State File Corruption = Crash

**Severity:** 🟡 High
**Location:** `src/state.ts` — `loadSearchState()`, `loadOptionsState()`
**Impact:** If `~/.voyagier/last-search.json` contains invalid JSON (disk error, interrupted write, manual edit), the CLI crashes with an unhandled JSON.parse error.

**Fix:** Wrap state file reads in try-catch. On corruption: delete the file, warn the user, continue. State files are ephemeral — losing them just means re-running a search.

**Effort:** 30 minutes

---

#### 2.2 — `plans.ts` Is 1,145 LOC

**Severity:** 🟡 High
**Impact:** Hardest file to review, test, and maintain. Contains 10+ subcommands spanning CRUD, collaboration, social features (comments, voting), and item management.

**Fix:** Split into:
```
src/commands/plans/
├── index.ts           # Register all subcommands
├── crud.ts            # create, list, get, summary, update, delete (~400 LOC)
├── items.ts           # items, remove-item (~120 LOC)
├── sharing.ts         # share, collaborators, unshare, shared, invites (~250 LOC)
└── social.ts          # comments, vote (~200 LOC)
```

**Effort:** 2 hours

---

#### 2.3 — No Structured Error Codes

**Severity:** 🟡 High
**Impact:** Error messages are human-readable strings. An agent can't programmatically distinguish "auth failed" from "plan not found" from "Sabre timeout" from "invalid input."

**Fix:** Define an error code enum:
```typescript
enum CliErrorCode {
  AUTH_FAILED = "AUTH_FAILED",
  NOT_FOUND = "NOT_FOUND",
  VALIDATION = "VALIDATION",
  API_ERROR = "API_ERROR",
  NETWORK = "NETWORK",
  STATE_CORRUPT = "STATE_CORRUPT",
}
```
Include in `--json` error output: `{ "error": true, "code": "NOT_FOUND", "message": "Trip plan abc123 not found" }`

**Effort:** 2 hours (combines with 1.1)

## Strategic Assessment

### What the CLI Does Well

1. **Complete booking pipeline** — plan → search → select → customize → cart → book → confirm. No gaps.
2. **CLI↔Web parity** — Everything done in CLI is visible at `voyagier.com/plans/{id}`. This is the killer feature.
3. **Minimal dependencies** — 2 runtime deps. Fast install, no supply chain risk.
4. **Clean auth** — PAT tokens, Bearer header, same guards as web app. No token exchange needed.
5. **Good composability** — Each command does one thing, outputs JSON, chains via shell.

### What's Missing for the Business

| Gap | Impact | When to Build |
|-----|--------|---------------|
| **Activity/excursion search** | Hotels and flights only — can't search tours, restaurants, events | When nest-api adds activity search (not CLI's problem) |
| **Advisor dashboard** (`voyagier status`) | Quick overview of all active plans, pending bookings, recent activity | After v1.0 launch — depends on advisor adoption |
| **Template system** | Reuse common trip patterns (e.g., "Cabo weekend" template) | After v1.0 launch — power user feature |
| **MCP server mode** | Exposes CLI as MCP tools for Claude Desktop, VS Code, etc. | When MCP ecosystem matures. Design doc already plans for this as Layer 3. |

### MCP Readiness

The codebase is well-positioned for MCP. Each command maps cleanly to a tool. `--json` output is the tool response. The only work needed:
1. `voyagier mcp` entry point that starts an MCP server
2. Tool definitions generated from Commander.js command metadata
3. JSON schema for each tool's input/output

Estimated effort: 1–2 days when the time is right. Not urgent — CLI-first approach works with every agent today.
